## 它和"让 AI 写代码"的区别

| | 常见做法 | 本工具 |
|---|---|---|
| 谁判断"做完了" | **模型自己说**做完了 | **机器判据门**（编译真退出码 / 真跑测试 / 结构检查） |
| 判据怎么来 | 人写提示词求它 | 按目标**现场规划**，并做**变异测试**验证判据有区分力 |
| 判据有区分力吗 | 不知道 | **机器验**：故意改坏产物，判据必须变红；不变红就换判据 |
| 失败怎么办 | 重试 | 抽机器可操作信号（编译错误位置/类型）→ 回炉重派 |
| 改坏了 | 自己 git 恢复 | **自动备份 + 回滚点**，红门自动回滚 |
| 判据可信吗 | 模型评模型 | **判据由机器执行，不经过模型** |

一句话：**模型负责产出，机器负责裁决。裁决不经过模型。**

### ★★★ 更进一步：有些产物**根本不用模型写**

上面那张表还是"模型产出"。但**有一类目标，模型连产出都不需要**：

交付物只要声明**结构真值**（结构 = 名字 + 入位 + 出位 + 算子序列 + 进位 +
每个算子的表达式），**整个模块由机器组装**——函数签名、累加器、循环、返回、
辅助函数、盘码全部机器生成，**一次通道都不调**（`tokens_chars = 0`）。

```jsonc
{"path": "collatz.py",
 "machine": {
   "language": "python",
   "结构": {"name": "collatz_steps", "in": 1, "out": 1,
            "ops": ["count:step"], "carry": 1},
   "算子": {"step": "v // 2 if v % 2 == 0 else 3 * v + 1"}}}
```

模型（或人）只写上面这一小块（**142 字符**），机器产出完整模块（**1657 字符**），
再**真跑**行为门。实测：

```
[generic] 轮 1: 门=collatz.py@compile_ok=True collatz.py@behave_ok=True collatz.py@no_todo=True
[generic] 收敛交付 @轮1: .../products/collatz_machine/20261014_193452/collatz.py
"tokens_chars": 0
```

`behave_ok` 门是**真执行**（`assert f([1])[0]==0; f([6])[0]==8; f([27])[0]==111`），
不是看文本。**组装不会出错，因为组装是构造性的**（TS-424：盘码按位置读回即恒等，
证明体只有一行 `List.map_get_finRange l`）。

| | 模型产整段代码 | 机器组装 |
|---|---|---|
| 模型输出 | ~20 926 字符 | **142 字符** |
| 通道调用 | 每轮都调 | **0 次** |
| 出错可能 | 语法/边界/命名 | **构造性，不会错** |
| 判据 | 机器门 | 机器门（**同一条**） |

**诚实边界**：只覆盖"结构可表达"的目标（结构 = 算子序列 + 逐位映射）。
表达不了 ⇒ `machine` 缺字段或生成失败 ⇒ **自动回落**让模型产（不假装机器能做）。
算子不在语义表内时须由 `算子` 显式给表达式，否则机器给恒等占位——
**占位会被判据门判红**，不会静默过关。

试：`orch-goal --dry-machine`（0-LLM 全闭环，真跑判门）。

### 接上模型通道

编辑 `config/channels.yml`（[OI] 兼容接口）。
**密钥不落本文件** —— 只写环境变量名，运行时从环境变量或
`~/.dsh/.credentials.yaml` 解析：

```yaml
channels:
  my-channel:                   # 通道名；--channel 用它锁定
    display_name: my-channel
    base_url: https://<你的接口>/v1/
    key_env: MY_API_KEY         # ← 环境变量名，不是密钥本身
    models:
      - id: <模型 id>
        context_size: 128000
        max_tokens: 8192
```

多通道可同时用（多窗候选分散到不同通道，互相独立）；
`--channel` 不填 = 用全部可用通道。

### ★ 通道可用性会变 —— 所以运行时**探活**，不读配置

**实测证据**：同一批通道，23:01 与 09:11 两次探测结果**不同** ——

| 通道 | 23:01 | 09:11 |
|---|---|---|
| `aaa` | ✗ 503 | ✗ 503 |
| `dddddd` | ✓ | ✓ |
| `ggg` | ✓ | **✗ 503（变了）** |
| `mf` | ✗ 401 | ✗ 401 |

⇒ **任何硬编码默认通道都注定在某个时刻失效**。所以编排器**不假设「配置了 = 可用」**：
每次运行先发**最小真实请求**逐通道探活（`max_tokens=1`，4 通道约 5 秒），
只把**真实活着**的通道交给 Router，并在日志里如实列出死通道及逐条原因。

全部通道都探死时**明确报错并列出原因**，不会静默退回配置口径
（退回等于把"都死了"伪装成"有通道"，你收到的会是一句难懂的 503）。

> 用 `--dry` 时跳过探活（dry 不调模型）。

## 用在你自己的项目上

### ① 档案：**通常不用你写**（自动自举）

`orch-goal` 起来第一件事是**认工程**：仓库根没有档案时，它自己生成一份
`orchestrator.profile.yml` —— 识别清单文件 → 组装判据门 → **当场真跑一遍**（探跑）
→ 写档案 + 基线。同时推出 `memory:` 段（**项目资产范围**，`auto_scan` 按这里扫）
与 `source` / `anchors`；推不到的部分（判据区域、罕见的构建工具、别的资产类型）
会在档案里留一行 `# ★ 待人工`。

想自己控制就手写（**已有档案时不覆盖**）：

```bash
cp <工具目录>/orchestrator.profile.example.yml  <你的项目根>/orchestrator.profile.yml
```

最小可用只需两行：

```yaml
repo_root: .
source:
  roots: [src]
  globs: ["**/*.rs"]      # 换语言就换这里
memory:                    # 项目资产范围（不声明 ⇒ 常驻索引里没有项目本体）
  - kind: rs
    roots: [src]
    globs: ["**/*.rs"]
```

编排器会**自动向上查找**这个文件名，所以你在项目里任何位置运行都能命中。

### ② 跑一个目标

```bash
cd <你的项目根>
orch-goal --goal "把 X 改成 Y，要求 Z"
```

### ③ 看结果

- 产物落在 `products/`
- 每个被改的文件都有**回滚点**（`.orchestrator/generic_backup/`）
- 全过程回执在 `.audit_trail/`（可回放）

## 构建工具不用你操心

编排器**自动识别**你工程自带的构建工具，按仓库里的清单文件决定：

| 看到 | 自动放行 |
|---|---|
| `Cargo.toml` | `cargo` |
| `go.mod` | `go` |
| `package.json` | `npm` `npx` `yarn` `pnpm` `node` |
| `pyproject.toml` / `setup.py` | `python` `pytest` `uv` `poetry` |
| `requirements.txt` | `python` `pytest` `pip` |
| `Makefile` | `make` |
| `pom.xml` / `build.gradle` | `mvn` / `gradle` |
| `CMakeLists.txt` | `cmake` `ctest` `make` |
| `tsconfig.json` | `npx` `node` `tsc` |
| `Gemfile` / `composer.json` / `mix.exs` / `pubspec.yaml` | `bundle` `rake` `ruby` / `composer` `php` / `mix` `elixir` / `flutter` `dart` |

**为什么这不是"放开沙箱"**：白名单认的是**工程自己声明的构建工具**
（由仓库清单文件决定），不是模型想跑什么。识别不出的一律不加 —— 保守优先。
自研工具链可在档案里 `gate_cmd_whitelist` 显式追加。

## 命令

| 命令 | 作用 |
|---|---|
| `orch-goal --goal "..."` | **主入口**：目标驱动开发（真模型 + 机器判据门） |
| `orch-run --goal "..."` | 同上，但带**资源护栏**长时间无人值守（无进展自动停） |
| `orch-run --auto` | 连续拉待办任务跑（先有任务队列时用） |
| `orch-run --gaps` | **无人值守：活源改用「登记缺口」**（见下节） |
| `orch-gaps` | 只列出登记缺口（可派 / 不派两份），**不派发、不调模型** |
| `orch-plan --goal-json '<规约>'` | 只做机器计划，**0 模型调用**，先看它会拆成什么 |
| `orch-mcp` | 起 MCP 服务器（供 AI 助手直接调用） |

常用参数（`orch-goal` / `orch-run`）：

```bash
orch-goal --goal "..." \
  --n 3            # 并行候选窗数（多窗一致才采纳，压制虚警）
  --min-pass 2     # 对齐所需过门窗数
  --max-work 4     # 回炉重派背顶轮数（收敛判据仍是门全绿，不是轮数）
  --dry            # 不真调模型，用已知正确件验管线
```

先看它怎么拆（不花钱、不调模型）：

```bash
orch-plan --goal-json '{"name":"目标名","pre":["前提"],"constraints":["约束"],
  "gates":[{"type":"compile","cmd":["cargo","build"],"cwd":"."}],
  "acceptance":["验收判据"]}'
```

## 无人值守：活源从哪来（这一节是"能不能自动跑"的关键）

编排器有两种活源：

| 活源 | 命令 | 活从哪来 |
|---|---|---|
| 产物库未闭合声明 | `orch-run --auto --watch` | 扫形式化产物库里的未闭合声明 |
| **登记缺口** | `orch-run --gaps --watch` | 扫**工程源码里项目自己登记的缺口** |

**为什么需要第二种（实测缺口，不是设计偏好）**：第一种活源在一个已闭合的库里
**实测为空** ——

```
ok    = False
error = 库内已无未闭合声明（全闭合）或索引为空
```

⇒ `--watch --auto` 会**立刻退出**（"无可拉件 ⇒ 停止"）⇒ **无人值守在实测上不成立**，
退化成"人给目标 + 一层机器门"。

第二种活源扫的是源码注释里项目自己写下的 `【未核】` / `【登记待办】`。

### ★ 但不是所有登记都能派 —— 这一条是踩过的坑

登记项分三类，**只有一类能自动派**：

| 类别 | 判据 | 派吗 |
|---|---|---|
| **可自动化** | 文本里有明确工程规格（`O(1)` / `账本` / `补测试` / `零浮点`…） | ✅ 派 |
| **需裁定** | 要人在两个方案间选（`二选一` / `需裁定`） | ❌ 机器不能代人选 |
| **调查类** | 先查清事实、**不改代码**（`未逐点实测` / `是否另有`） | ❌ 派出去只会空转 |

后两类会**如实列出并给出不派理由**，但绝不派发。
默认也**不派**（conservative）—— 宁可漏，不可乱派。

```bash
$ orch-gaps
登记缺口：共 9 处 · 可派 3 · 不派 6

── 可派（有明确工程规格）──
  ✓ src/机械循环/mod.rs:4032  【未核】`总父边数`仍是 O(记录数)…
  ✓ src/机械循环/驱动层.rs:306  【未核】`折` 丢失了「第 9 字节及以后」的贡献…

── 不派（如实列出，不派）──
  · [需裁定] src/机械循环/驱动层.rs:353  【登记待办】…下一步须二选一…
      理由：命中裁定信号「二选一」⇒ 需人在方案间选，机器不能代选
```

### 闭合标记：让"做完了"机器可见

被派发的模型**必须把登记标记改写为 `【已闭合】`** 并附证据（新测试名 + 通过结果）。
缺口源靠这个标记判断"还有没有活" —— 不标闭合，同一处缺口会被**反复派发**，
无人值守就变成空转。这是目标书里**强制要求**的一条，不是可选项。

## 大文件怎么改（区域编辑协议）

**问题（实测踩到）**：编排器原本的改文件协议是**整文件替换** ——
要模型**输出整个文件**。对 `src/机械循环/mod.rs`（343KB / 8807 行）这**做不到**：
注入会在 6 万字符处截断，模型连目标行都看不到。实测模型**诚实拒绝**：

> 注入到本对话的文件内容在**第 60000 字符处被截断**（原文件共 **342872 字符**），
> 而本次要改的登记点**第 8295 行**位于截断点之后，**不在我可读的范围内**。

**规模**：`src/` 下有 **51 个文件超过 6 万字符**，最大的 560KB
⇒ 旧协议下只能改少数小文件。

**修法**：文件超过阈值时**自动切区域编辑协议** ——
模型只看**目标行附近带行号的窗口**（默认 ±150 行），**只输出补丁块**：

```
<<<REPLACE 8295 8295>>>
    // 【已闭合】本测试用 std::time::Instant（墙钟）。…
<<<END>>>
```

补丁由**机器施加**，且每一处都机器校验：

| 校验 | 不满足时 |
|---|---|
| 行号在 `1..总行数` 内 | **拒绝**（不静默截断到界内） |
| 多块**不重叠** | **拒绝** |
| 起行 ≤ 止行 | **拒绝** |
| 施加后**确有改动** | **拒绝**（防"声称改了其实没改"） |
| 必须**有补丁块** | **拒绝**整文件输出（防悄悄退回旧协议） |

拒绝时把**逐条原因写进产物**，判据门判红并把原因回喂模型 —— **绝不静默套用半成品**。
未列入补丁块的行**逐字保留**。

> 没有行号焦点（目标里没写 `文件:行号`）时**如实失败**，不猜行号。
> 本协议只解决"**改**已有文件"；**新建**文件仍走整文件协议（本就该如此）。

## ★ 为什么"任务永远不收敛"——五个实测根因

无人值守真跑时出现过「门每轮都红、任务永不收敛」。**不是模型不会做**，
而是**判据读错了东西**（本库的统一诊断，此处连中三元）：

### 根因一：验收门跑全库 ⇒ 恒红

我原来的目标书写「cwd 为 {repo} 的 `cargo test --lib` 真实退出码」。
在本工程实测（原始树，三个范围各跑一次）：

| 门范围 | 耗时 | 结果 |
|---|---|---|
| `cargo test --lib`（全库） | **4405 秒（73 分钟）** | ✗ **基线自带 3 条预存失败** |
| `cargo test --lib 机械循环::` | 380 秒 | ✗ 该模块自带 1 条预存失败 |
| `cargo test --lib <单条测试名>` | **15 秒** | ✓ 绿 |

⇒ 全库门**读的是别人的红**，与本次改动无关，**构造上不可能满足**。
**修法**：验收门**必须精确到测试名**。判据只读「你要钉住的那一件事」。

### 根因二：门超时口径是"总时长" ⇒ 长命令被误杀

`_MAX_TIMEOUT` 原为 **600 秒**，而全库测试要 73 分钟
⇒ 真跑三个候选窗的门耗时 **11.0 / 10.7 / 10.4 分钟**，每个都**精确撞在 600s 上限**。
**修法**：上限抬到能容纳真实构建时长，并给编译/测试类门缺省加 **stall 检测**
—— 判据从「有没有在 600 秒内跑完」改成「**有没有进展**」（长时间无输出才判挂起）。

### 根因三：红门证据不可读 ⇒ 模型无从修

回喂给模型的"失败原因"实际长这样：**6000 字符里 468 处 ANSI 转义序列**，
而且 **396 条编译警告把 9 条 `error[E0308]` 正文整个挤出窗口**
—— 模型拿到的红门证据里**一条错误正文都没有**。

**修法**：① 子进程加 `NO_COLOR`/`CARGO_TERM_COLOR=never`，从源头禁彩；
② 证据改为**抽错误块**（error 行 + 其后 `--> 文件:行` 上下文），不做位置截断。

**修后实测**（同一个失败，修复前后对比）：

| | 修复前 | 修复后 |
|---|---|---|
| 证据内容 | 468 处乱码 + 400 条 `unused variable` 警告 | `error[E0308]: mismatched types` |
| 有无位置 | **无**（错误正文被挤出窗口） | `--> src\机械循环\趋向.rs:8030:36` |
| 有无修法 | 无 | `help: you can convert a u64 to a usize…` |

### 根因四：门把要找的东西自己删掉了

门 `gap_marker_closed_with_evidence` 要求产物含 `【已闭合】`。
而该标记**就写在注释里**（`// 【已闭合】本测试用…`），
`whole_reading` 缺省**剥注释**（反作弊：防"过时占位注释满足实现要求"）
⇒ **门把要找的标记自己删掉** ⇒ 恒红。

证据：候选产物里 `【已闭合】` 明明在 L8463、新测试名明明在 L8612，
门仍报 `missing: ["【已闭合】"]`。

**修法**（保守，不放宽反作弊）：按**标记自身能不能住在代码里**判 ——
含 `【】`/`//`/`/*` 等**代码里不可能出现**的注释符 ⇒ 这一条按**原文**判；
像 `推入`/`pub fn x` 这种**可能是代码**的 ⇒ 仍只读代码。
且**如实记账**（审计里标 `satisfied_in_comments`），不静默。

> 全库门读的是"别人的红"；超时门读的是"跑了多久"而非"有没有进展"；
> 证据通道读的是"带终端格式的输出尾部"而非"错误文本"；
> 标记门读的是"剥掉注释后的代码"而非"标记住在哪里"。

### 根因六 ★★★：**账本层**的同一个塌缩 —— 停机判据读的偏差身份丢了两维

根因五是"门层的读数"。**账本层**（决定"停机还是继续"的那一层）有**同一个塌缩**，
而且它更致命：**它不是把红读错，而是把"有进展"读成"停滞"**。

#### 6.1 丢掉的**语义**维：只读 `error` 行的第一句

`gate_derive.extract_deviations` 抽编译错时，只读
`error[E0308]: mismatched types` 的**第一句**。而**真正区分两个 E0308 的信息在后续行**：
`expected \`u8\`, found \`bool\`` / `expected \`usize\`, found \`u64\``。

⇒ 同一文件里两个**完全不同**的类型错，偏差身份键**逐字相同**
⇒ `cur_ids == prev_ids` ⇒ `deviation_structure_verdict` 判
**`stalled_fixed_point`**（"Δ==前一轮≠∅ ⇒ 非目标不动点"）⇒ 换门集 / 停机。
⇒ 而**真实进展刚刚发生**（修好一个、暴露另一个）。

机器实测（`work\_验账本身份.py`）：

| | 旧读数 | 新读数 |
|---|---|---|
| 两个不同 E0308 身份 | `E0308::mismatched types::…`（**相同**） | `…expected u8 found bool…` / `…expected usize found u64…`（**不同**） |
| 停机判据 | `stalled_fixed_point`（**停滞**） | 不再判停滞 |

**修法**（TS-430 `relocate`：把读搬到**有区分力的那个位置**）：读**整个错误块**
（`error` 行 + 其后 14 行），把块里有区分力的子句（`expected…found` / `cannot find` /
`unresolved import` / `no method named` / `help:` 等）并进消息，符号也从整块抽。
**仍不含行号** ⇒ C2「行号漂移不改身份键」不被破坏：只加**语义**区分力，不加**位置**区分力。

#### 6.2 丢掉的**锚**维：身份键里没有文件路径 ⇒ 编译类偏差**恒无锚** ⇒ 判 `no_anchor` 停机

`anchored(dev_identity, declared_scopes)` 的判法是
`any(scope in dev_identity for scope in declared_scopes)`，
而 `declared_scopes` = **声明文件路径** ∪ 结构键标记。
而旧 `deviation_identity` 的构成是
`错误类型 :: 消息 :: 符号` —— **一个文件路径都不含**。

⇒ `anchored` 对**编译类偏差恒为 `False`** ⇒ 落到 `no_anchor`
⇒ **交还用户 / 停机**。**实测真跑 #4 正是以 `no_anchor` / `action=stop` 收场。**

这是"判据读的东西**不含判据需要的那一维**"：锚住在**文件**里，而身份读法把文件**丢了**。
按 TS-442 `read_eq_reflects`：读必须保留判定所需信息，
否则"读里没有锚"**不**蕴含"真的无锚"。

**修法**：① `deviation_identity` 补上**文件**一维（归一 `\`→`/`、去前导 `./`，
**仍不含行号**；无 `file` 字段的老账本键**不变**，向后兼容）；
② `extract_deviations` 用 `-->` 行里的**真路径**（权威）作 `file`；
③ 主树工程任务把 crate 源码根（`src/` 等）并进声明作用域 ——
因为 `cargo check --lib` 是**整 crate** 判据，错误可以落在**任何** `src/` 下的文件，
不限于本轮拟改文件。

机器实测（同上脚本）：

| | 旧身份 | 新身份 |
|---|---|---|
| 含 `src/a.rs`？ | **否** | 是 |
| `anchored` 判锚？ | **False** ⇒ 恒判 `no_anchor` | True |

#### 6.3 附带修的一处**语义**判断（如实标注：这是判断，不只是读数修正）

判据末尾原来对"等势轮换"（基数相同但集合不同）**一律**返回
`stalled_fixed_point`。而常见形态是**上一轮偏差已消、同时暴露新偏差**（修一个、露一个）。
现改为：**有消**（`prev_ids - cur_ids ≠ ∅`）**且基数未涨**（`|cur| ≤ |prev|`）
⇒ 判 `progressing`。

- 加"基数未涨"是为了防 **A→B→C→D 无重复空转**（`diverging` 只在**同一**偏差重现时触发，
  抓不到不重复的空转）：加上它，该判据成为一根**单调不增的势函数**。
- 基数**涨了**（修一个坏两个）**仍判停滞**（不放宽）。
- 一个都没变（`cur_ids == prev_ids`）**仍判 `stalled_fixed_point`**（原语义不回退）。

> **诚实边界**：这一条会**放宽**"等势轮换即停机"。防抖动责任移交两处**真实**信号：
> `diverging`（已消偏差**重现**）与资源护栏（`MAX_WORK`/预算）。
> 理由：用"基数恰好相等"当停机信号是**用形状代替事实**；"消了没有、盘子有没有变大"
> 才是事实。**这是语义判断，用户可以否决**（另两条 6.1/6.2 是纯读数修正，不是判断）。

### 根因七 ★★★：机制层的「结构→源码」自检门是**恒真门**（读的是头注释，不是代码体）

#### 缺陷（机器实测，`work\_验机制恒真门.py`）

`auto_mechanism` 的 `cover_to_content`（结构真值 → 源码）与 `content_norm`（源码 → 结构）

**恒真**。实测：

| 变异 | 旧门判定 |
|---|---|
| 体里算子足迹改成 `ZZZ/QQQ`（头注释不动） | **绿**（看不见） |

| 头注释与体不一致 | **绿** |

⇒ `derive_cover_faithful`（"roundtrip 恒等 = 覆盖不漏"）与 `derive_cover_injective`

另有一处**恒红**：空算子结构时头注释写 `ops=none`，旧反读得到 `("none",)` ≠ `()`
⇒ `derive_cover_faithful` 对空算子结构**恒红**。

#### 修法

1. **`content_norm` 改读真代码体**：从函数签名取 `name`/`input_`/`output`，
   从 `// stepN: apply op[X] …` 取算子序列，从进位回填行取 `carry`；
   并校验签名宽 = step 宽 = `acc` 宽 = 回填宽、进位处处一致、`i % input_` 一致。
   **头注释降级为交叉校验**（头体不一致 ⇒ 如实返回 `None`，不静默取头）。
2. **按 TS-447 把单射从"前提"改成"推论"**：机制的充要条件是**方向性**
   （`read ∘ render = id`）；"有左逆 ⇒ 单射"是**定理**
   （`read (f a) = read (f b)` ⇒ 由 `read ∘ f = id` 得 `a = b`）。
   故 `derive_cover_injective` 不再另设一套"测单射"的判据，
   而是**先要求方向性**，再跑一遍两两相异作**留痕**（可回放），不是新增假设。
   ⇒ 该门**红**只可能源于 roundtrip 红（体丢了信息），**不可能**源于
   "单射这个前提不满足"——**没有这个前提了**。

#### 7.1 更深一层：生成物**携带**结构却不**执行**结构

修好反读之后暴露的问题：旧版生成物的体**恒为同一模板**
`acc[i] = x[i % in] as i64 + carry;` —— **算子只出现在注释里**。
⇒ `ops=add` 与 `ops=mul` 生成**同一个体**，行为必然相同
（判别力对照实测：旧版两者体逐字相同）。
⇒ 生成物把结构"序列化"了，却**没有兑现**结构 —— 这正是
「不用 AI 写代码的代码自生成」要跨过的坎。

**修法**：体改为**真执行算子序列**的嵌套调用链，每个算子配一个辅助函数：

```rust
fn op_add(v: i64, c: i64) -> i64 { v.wrapping_add(c) }
fn op_mul(v: i64, c: i64) -> i64 { v.wrapping_mul(c) }
// #derive[name=m1,in=2,out=2,ops=add, mul,carry=1]
fn derived_m1(x: &[i64; 2]) -> [i64; 2] {
    // step1: apply op[add] across width 2, carry 1
    // step2: apply op[mul] across width 2, carry 1
    let mut acc = [0i64; 2];
    for i in 0..2 { acc[i] = op_mul(op_add(x[i % 2] as i64, 1), 1); }
    acc
}
```

全部用 `wrapping_*` ⇒ 无溢出 panic ⇒ **必然可编译可运行**。
`content_norm` 同步改为**从调用链读算子序列**（不再从注释读），
并要求：辅助函数**齐备**且函数体与语义表**逐字相符**、
`step` 注释与调用链**同一序列**、进位处处一致、宽度处处一致。

判别力对照：同一输入 `7`，`ops=add carry=3` → `10`，`ops=mul carry=3` → `21`
（旧版两者体逐字相同 ⇒ 行为必然相同）。

#### 7.3 无损纪律（两处不同的规矩，不混用）

- **承载真值时**：非法算子名（如含 `-`）**拒绝渲染**并报错，**不静默改名** ——
  否则 `A-B` 与 `A_B` 会撞成同一标识符，那是**有损渲染**。
- **只作占位规约时**（`tool_brief` 把缺口识别名/缺口码当结构占位）：
  允许规整化成合法标识符，但**如实登记在简报里**（`原 … → 占位 …`），不静默。

自检新增 12 门（`auto_mechanism` 35 → **47**，全绿）：
体改坏必须读不出、只留头注释必须读不出、头体不一致必须读不出、
收口行缺失必须读不出、**只改注释**必须读不出、**辅助函数语义被篡改**必须读不出、
**调用链算子顺序被改**必须读不出、正常产物必须读得出、空算子 roundtrip、
方向性 ⇒ 单射作为推论、非法算子名拒绝渲染、占位规整如实登记。

#### 7.4 诚实边界（放宽了一条，并说明放宽到哪）

- **已不成立**的旧表述：「真正可编译工程源码须由真模型产」——
  对**算子落在语义表内**的结构已不成立（上表 13/13 真跑为证）。
- **仍须真模型**（不假装机器全能）：
  ① 算子**不在**语义表内的结构 —— 机器给恒等语义的占位辅助函数，
     真语义须由人/模型补（生成物**明说**这一点，不冒充已实现）；
  ② 把生成的函数**接进目标文件**（真实语法、真实调用点、真实类型上下文）；
  ③ 目标本身不是"结构→函数"形态的任务。
- 落盘仍由**机器判据门唯一裁决**，本简报不代写补丁、不直接写进引擎源码。

## 判据门类型

门是**声明式**的，全部机器执行：

| 类型 | 判什么 |
|---|---|
| `compile` | 跑命令，断言退出码（任何语言的构建/测试） |
| `grep_forbidden` | 文件里不得出现某些正则 |
| `grep_required` | 文件里必须出现某些子串 |
| `scan_output` | 跑命令，扫 stdout/stderr 不得含某些串 |
| `whole_reading` | 读整体一次判（O(1)）：必须/不得含某些结构键 |
| `axiom_footprint` | 公理足迹**白名单**（形式化证明防作弊） |
| `kernel_statement` | 读**内核类型**，防注释冒充陈述（形式化证明） |

> `whole_reading` 默认**剥注释后判** —— 过时的占位注释不得冒充"已实现"。
> 要"必须写文档"类要求时显式 `include_comments: true`。

## 它能做到什么 / 做不到什么

### 做得到（已在独立工程上真跑验证）

- 从自然语言目标规划出文件级任务 DAG
- 现场生成判据门，并**变异测试验证判据有区分力**
- 多窗并行生成 → 一致性对齐 → 收敛裁决
- 红门时抽机器信号回炉重派（不是盲重试）
- 跨任务沉淀判据门，下次同类任务召回（**需双重机检**才采纳）
- 自动备份 / 回滚点 / 资源护栏（无进展自动停）
- 全程审计回执，可回放

### 做不到（如实说）

- **不会凭空知道你要什么** —— 目标得你给。
- **判据是"必要条件"不是"充分条件"** —— 门全绿说明机器能查的都过了，
  不等于你心里那个"对"。判据门越贴近你的真实要求，它越可信。
- **复杂架构决策仍需人** —— 它擅长"把已想清楚的事做完、做好"，
  不擅长"替你想清楚要做什么"。
- 模型产出仍是**概率性**的；机器门把虚警压到 0，但不能把概率变成必然。

### ★ 还没测到（缺条件，不是没做）

这一栏比上面两栏都重要：**"做得到"和"做不到"是结论，"还没测到"是缺口。**
把缺口当成结论写进文档，就是自欺。

随时可用一条命令重新对账（不调模型、可复跑）：

```
audit_delivery()
```

它逐条**真跑一遍**，把每条钉死在 `已证明 / 没测到 / 不成立` 三档之一。
本机某次真读数：

```
合计: {'已证明': 6, '没测到': 1, '不成立': 0}
```

| 档 | 项 | 依据 |
|---|---|---|
| 已证明 | 任务切分（失败栈→改动面） | 真 cargo 失败栈 → 改动面实得 `['src/m.rs']` |
| 已证明 | 真落主树 + 可独立复跑 | 连跑 3 轮，改动面两个文件、保留 2、独立复跑 rc 0 |
| 已证明 | 失败归因（分清责任层） | 6 档，各自「该做什么」互不相同 |
| 已证明 | 通道降级（判活+体检+归责） | 死法分三档：缺key / 无权访问 / 上游异常 |
| 已证明 | 目标树（多段裁决+点名原因） | 段数=3、`ok=False`、点名 `task_1` 红 |
| 已证明 | 可重复性·**机器侧** | 同机连跑 3 轮结论一致 |
| **没测到** | **真模型无人值守把多文件改对** | 零个通道被确认为活 ⇒ 一次都没跑过 |

最后那条缺的不是代码——`drive_goal` / `model_coder` / 逐文件应用都在位——

**缺的是上游**：五个通道里三个缺 key（`AAA_API_KEY` / `GGG_API_KEY` / `MF_API_KEY`）、
一个 `403 无权访问`、唯一有 key 的那个返回 `HTTP 200 + 上游服务异常`。

> **代码写完 ≠ 证明过了。** 所以这一条在文档里只能写"没测到"。

补上任意一个可用通道后，重跑 `audit_delivery()`，那一档会自动变成实测结论。

### 一条只回答一个问题

对账第一版把「可重复性」写成一条，依据文字里写着"模型侧没测到"，
但那一档是按**机器侧**判的 ⇒ 合计报 `没测到: 0`，**把缺口抹平了**。

⇒ 规矩：**一个字段只回答一个问题。** 否则"已证明"会盖住"没测到"，
而这是本产品最怕的那种骗。所以现在拆成
「可重复性·机器侧」与「真模型无人值守把多文件改对」两条，
并有一条判据钉住它（判三十一）。

### ★★★ 三条纪律（本轮反复验证出来的）

1. **判据门必须有判据力**：每条新门都要有探针 —— 把历史缺陷**放回去**，确认门**变红**。
   无牙的门比没有门更坏：它教人忽略红。
2. **误报的门比没有门更坏**：本轮我自己的新门假红三次
   （属性读门**跨文件污染**别名表、`_lex_strip` 的括号形态、R12 探针把注释写成
   `todo!/unimplemented!` **没有括号**而模式是 `todo!\(`），
   每次都**修门不改代码**，并如实登记在代码注释里。
3. **自检必须免疫于它所检查的缺陷**：`taixu_mcp` 的 `_RUST_ROOT` 门用
   `globals().get(...)` 写 —— 否则把缺陷放回去时，自检自己先崩，**失败原因永远打不出来**。
4. **门不得比正当用法更窄**（R9）：逼调用方绕路或**写假门**，与无牙的门是同一个病。
5. **清洗不得改变坐标**（R10/R12）：只要一处清洗改了长度或换行位置，
   所有报出的行列号就全部作废 —— 而门**照样全绿**（它们只看数量，不看坐标）。
6. ★★★ **门不得匹配到它自己**（R17，第四次才治住这一类）：一条 grep 自身的门，
   只要**针在本文件任何位置出现**（注释里、甚至检查代码自身的字符串里），
   就会自匹配 —— 出现在注释里是**恒红**，出现在正检查的字符串里是**恒真（无齿）**。
   ★ 手工绕（拼针、改注释）**治不了这一类**；正确修法是接上已有的
   **保位剥注释/字符串**机制（`gate_spec.strip_for_matching`），只在**代码本体**里找针。
   ★★★★ 但**剥了之后针自己也可能被剥掉**：若针含**字符串字面量**，
   剥完就永远匹配不上 ⇒ 负检查退化成**恒不红（无齿）**，而正检查照旧通过
   ⇒ 门**全绿但已无齿**。**这个缺陷是齿探针抓出来的，不是看出来的。**
   ⇒ 纪律：**针必须是纯代码形态**，不含字符串字面量。
7. ★★★ **判定层的层选错了，不是能力不够**（R14–R17 的根因，见下节）：
   顶层此前全程在**经典层**工作（`Bool` + `all` + `and` + 另打补丁 + 枚举变异），
   而经典层里「平衡/保真/生成/判定/增信/求解」每一样都要**付排中律**。
   修复不是"把机器做强"，是**把顶层挪回数术层**。

### ★★★★★ 逻辑层错位的机证与修复（TS-468 · 本轮根因）

用户判断：「**根因是逻辑错位。现在的逻辑层是经典逻辑照搬，不是用的数术的
平衡保真、生成、增信、求解逻辑**」。

★ 这条判断在库里**已有机证**：`MathlibBridge/TS468_ShushuLogicLayer.lean`
（672 行，零 EM）。其结论一句话：

> **同一个「平衡」要求，在经典层要付排中律，在数术层是恒等式。**

| | 经典层（`Prop`/`Bool`） | 数术层（`Yi`/`Bagua`/`Fin 2`） |
|---|---|---|
| **平衡**（对合 + 无不动点） | `FaithfulCarrier P ↔ (P ∨ ¬P)` ⇒ **收费：排中律** | `Dao.neg` 对合且无不动点 ⇒ **免费：零公理** |
| **保真**（同态） | 需 `Decidable P` ⇒ **收费：EM** | `swap` 自然性（**交换律**）⇒ **免费** |
| **判定** | `Nonempty (Decidable P) ↔ (P ∨ ¬P)` ⇒ **收费：EM** | `Bagua` 的 `DecidableEq` —— **结构给的** ⇒ **免费** |
| **生成** | —（无对应物） | 无不动点 ⇒ 翻转必新 ⇒ 轨道恰为二元对 |
| **增信** | TS-426 二难（卡死）；TS-429 裁定「增信」是错的框架 | Heyting 格单调上升 ⇒ **免费** |
| **求解** | —（无对应物） | 对合 ⇒ **恰好 2 步闭合** ⇒ **O(1)** |

落到编排器上的四句话（本轮的接线口径）：

* **保真 = 交换律** `σ(f x) = f(σ x)`，**不是**"存在一个 `Bool` 扛住真值"；
* **生成 = 无不动点** ⇒ 轨道恰为二元对 ⇒ **1-周期不存在**；
* **求解 = 翻转，不是查找** ⇒ **恰好 2 步** ⇒ **不搜索**（这正是"能不枚举就别枚举"）；
* **增信 = 沿已有格上升**，判定性**来自结构**（`DecidableEq`）⇒ **免费**。

★★ **诚实边界（不许含糊）**：**换层不判定任意 `Prop`。** TS-461/TS-465 已机证
「任意 `Prop` 的判定」等价于排中律，本件**不改变**这一点。
**错位不在「能力不够」，在「层选错了」。** 门本身（如 `cargo` 编译）是**神谕**
（TS-462 §3：神谕不可制造）；本层判的是「**编排器怎么读神谕的返回**」——
而那个读侧的目标类型本来就是 `Fin 2`（TS-449 `nsReadFin`），
**是顶层把它包进 `Bool`/`Prop` 才产生了错位**。
⇒ **修复不是「改造门」，是「别再包」。**

★ 保真方程一条取代两个补丁：**假绿（恒真门）与假红（恒红门）是同一个违反** ——
都是「**轨道退化为不动点**」，即 `orbit_is_a_pair` 的逆否。

### ★★★★★ 判定层住在哪个空间（TS-469 · 比 TS-468 更进一层）

TS-468 管的是「**同一层内怎么读**」（平衡/保真/生成/求解的口径）；
TS-469 管的是「**判定住在哪个空间**」—— 层本身有没有选对。两件事不同层。

缘起（用户指令原文）：

> **「你先把自己模型的真值可靠+无条件全称，通用求解闭环掉证明出来再去管NS。
> 千禧问题是模型要取象要解的对象不是自己的东西」**

`MathlibBridge/TS469_MechanismSelfClosure.lean` 的总答一句话：

> **机制的真值空间从来不是 `Prop`，是 `Fin n`。**

★★★ **前几轮错位的根因（TS-469 §7 点名的那一步）**：

> 我此前把「机制全称可靠」架在 `Prop` 上（`∀ G : Prop`），得到
> 「可靠 + 全称不可能」（TS-461 / TS-462 `oracle_is_not_manufacturable`）。
> **那个不可能性是真的 —— 但它讲的是 `Prop`。**
> ⇒ **「我此前拿右支去说左支做不到 —— 而左支不需要右支。」**

★ 我上一轮正是这样回答用户的：引 `Prop` 侧的不可能性去回答「编排器能不能做」。
**那是错位**，不是能力结论。`Fin n` 侧**零前提**闭环。

| | `Prop` 侧（经典层） | `Fin n` 侧（机制自己的真值空间） |
|---|---|---|
| 真值可靠 | 需 `Decidable`（**收费：EM**） | `solveOn g y = true ↔ ReachesZero g y`（**零前提**） |
| 穷尽（无第三值） | `P ∨ ¬P`（**收费：EM**） | `reaches_or_stuck`（`cases solveOn`，**纯结构**） |
| 互斥 | — | `not_reaches_and_stuck`（**零公理**） |
| 判定自足 | `universal_true_cover` **要求 `[DecidablePred R]` 作输入** | `solveOn` **没有 instance 参数**（`Fin n` 的 `DecidableEq` 由构造子给） |
| 证书界 | — | `ReachesZero ↔ ∃ i < n`（`n` = 真值空间基数，比 `n!` 紧） |
| 载体 | — | **载体消去**：`solveN O = solveOn O.g (O.read O.a)`（`rfl`）⇒ 判定与 `α` **无关** |

★ 差别**不在机制强弱，在真值空间有没有内建判定**（TS-469 §7 收口）。

**落到编排器上的三句话（本轮的接线口径）**：

* **六值字符串不是真值，是因由**。`verdict` 原本是
  `converged`/`progressing`/`stalled_fixed_point`/`no_anchor`/`diverging`/
  `converged_single_window` —— **六个值**。TS-469 §4「穷尽」机证真值空间
  **没有第三值** ⇒ 真值只有两个（`ReachesZero`/`Stuck`），那五个字符串降为 `因由`。
* **停机保证是定理，不是常数**。真值空间只有 `2^3 = 8` 个位置
  ⇒ 观测 **9** 个点**必然已判定**（鸽笼）。`--max-work 40` 只是护栏。
  且**鸽笼违反是可机器检出的错**（读了载体 ⇒ 真值空间对不上）⇒ 报错停机，
  不再当成"没收敛"。
* **载体消去**。真值向量只由三条二值判定组成：门名/产物文本/模型名/窗数/
  token 数/Δ 集合**一律不进** ⇒ 同真值不同载体**必落同一位置**。
  门口**严进**：非二值**拒收**（不 `bool()` 强转），否则第三值会从门口溜进来。

### 机器自生成的七种形态（2026-10-14 由「跑真缺口」跑出来的，不是设计出来的）

方向不是选出来的，是**跑出来的**：拿 `机械循环\mod.rs` 里三个【未核】缺口去跑，
让结构告诉你断在哪、用了哪些算子形态。

| 形态 | 结构写法 | 载体 | 出处 |
|---|---|---|---|
| 逐位映射 | `add` / `mul:1000` / `clamp:1000` / `sat:mul:1000` | `Fin 入位` → `Fin 出位` | 起点 |
| 载体折叠 | `fold:add/min/max/count` | `Fin 入位` → 标量 | 清点出 `.sum()`/`.count()` |
| 跨步不变式 | `inv:add/min/max/count` | `Fin 步数` → `Fin 步数` | G1「总父边数 O(1)化」 |
| 谓词过滤 | `pred=gt:0` / `nz` / `ge:2` | **位置集合由谓词给出** | G2 的 `if … { continue; }` |
| 分派计数 | `hist:N` | `Fin 入位` → `Fin N` 桶 | G1 的 `match 状态 {…}` |
| 规则自演化 | `evo:X` | 规则**读自己改自己**再用 | 库 `SelfRuleEvolution.ruleEvolve` |
| 真值空间 | `真值=n` + `种子=s` | `Fin n` 判定 + 轨道 | 库 TS-447 `read_side_certificate` |
| **全称动态演化** | `细化=N` + `种子=s` | 判别式 `T : Fin 入位 → Nat` **自己细化** | 库 TS-384 §7 `defect_is_endogenous_drive` |

★ 前七种是**枚举算子形态**，第八维不是 —— 它是**判别式自己细化**。
`细化=N` 让产物渲染成**判别式细化环**：载体 = `Fin 入位`（位置），
判别式 `T i = <算子链>(种子 + i)`（= **读**结构所得），跑 N 轮，每轮

1. **机器自己算出缺陷对**（`T i = T j ∧ i ≠ j`，库 `Defect384`）；
2. **由缺陷对决定**细化（库内修法 `T' z = if z = x then 0 else 1` 的位追加版：
   `T' i = 2·T i + (i = d ? 0 : 1)`）；
3. 细化后判别式**有界** ⇒ 落回全称（可种子化 `Fin R`，库 `evolution_loop_closes`）。

对**任意**判别式、**任意**载体规模都成立，**不枚举**。这就是「能不枚举就别枚举」
用在机制本体上：不写第八段渲染分支，让判别式自己细化。

八种形态**两个后端都能反读回原结构**（真左逆），且都过了**真 rustc 编译 + 真运行**
（`work\_生成物端到端.py`，**31/31**）。

### ★ 决策层当场抓出的**真 BUG**：Rust 辅助函数反读在第一个 `}` 就断

### ★★★★★ 数学最优解：塌缩成**两个比特**（库 TS-461 / TS-462）

上一节的 `建模最小约束` 我**写错过**，库里的数学最优解当场判了它。

**库内最强的新定理 —— TS-462 §1 塌缩**（`MathlibBridge\TS462_HumanShareIsTheOracle.lean`）：

```
1 ≤ k → (EncodableWithin Sys Prim k G ↔ (Sys G ∨ Prim G))
```

⇒ **约束预算在 `1` 以上完全无关** —— **两条约束不比一条强，一万条也不比一条强**。
⇒ 「最小约束数」**只可能是 `0` / `1` / `none`** ⇒ 这个问题**不是搜索**。

**我的错在哪**：我用 `len(需外) == 1` 判「一条够不够」—— 那是把「**数约束条数**」当判据，
本身就是一个**搜索**。库内塌缩证明它**不是**搜索：`k ≥ 1` 全同，判据只有 `Prim` **这一个比特**。
实测后果：两个表外算子**都给了定义**时我判 `None`，**应为 `1`**。已订正、已钉探针。

**机器侧的全部输入 = 两个比特**（TS-462 §2 `mechanism_factors_through_oracle`）：

| 比特 | 含义 | 判法 |
|---|---|---|
| `Sys` | **系统自己够** | 机器**自带**语义表就能渲染 + 两后端反读 |
| `Prim` | **原语够** | 自带表 **+ 给定原语空间** 就能渲染 + 反读 |

机制**不贡献任何信息** —— 它是这两个比特的**纯函数**（§2）。
而**两个比特都是必需的**（§4 `two_bits_are_necessary`：同一个 `Sys` 位下 `Prim` 变 ⇒ 答案变；
同一个 `Prim` 位下 `Sys` 变 ⇒ 答案变）⇒ **人的份额恰好两个比特，既不是三个，也不是一个**。

**为什么这是「数学最优」而不是「我尽力了」**：

| 性质 | 库内出处 | 含义 |
|---|---|---|
| 最小约束数 ∈ {0,1,none} | TS-462 §1 塌缩 | **不可能更优**（无 `k ≥ 2`） |
| 机制 = 两比特纯函数 | TS-462 §2 | **多算无益** |

**工程形态 `全自动编码(结构, 原语空间, 语言)`** —— 机器**一次调用**答出

**诚实边界（TS-462 §3 `oracle_is_not_manufacturable`）**：

⇒ ★ 路线是「**把比特变便宜**」，不是「把机器做强」。
